# ADR-0005: PostgreSQL 16 as the metadata store

- **Status:** Accepted, with corrections
- **Date:** 2026-07-26

> **Correction, 2026-09-02.** Two details below never became true, and are recorded here rather than
> edited out, because an ADR is a record of what was decided and when
> ([ADR-0001](0001-record-architecture-decisions.md)).
>
> - **`sqlc` was never adopted.** There is no `sqlc.yaml`, no `sqlc` in `go.mod`, and no generation
>   target. Queries are hand-written against `pgx/v5`. The *reason* `sqlc` was chosen still holds and
>   is still honoured by hand: parameterized queries only, no ORM indirection. What was lost is the
>   compile-time checking, which is now a review responsibility.
> - **Migrations live at `internal/storage/metadb/migrations/`,** not at the repository root, so they
>   can be `go:embed`-ed and the control plane can migrate itself with no external files. That change
>   was made during the foundation work and recorded in the
>   [journal](../dev/journal/00-foundation.md).

## Context

The control plane stores tenants, users, environments, instances, connections, jobs, backups,
verifications, alerts, and an immutable audit log. This data is relational, requires transactional
integrity (a backup row and its verification row must not diverge), and must support multi-tenant
row scoping from day one.

## Decision

PostgreSQL 16, accessed with `pgx/v5`. Queries generated by `sqlc`. Schema migrations by
`golang-migrate`, with SQL files in `migrations/`.

- Every table carries a `tenant_id` from the first migration — retrofitting tenancy is far more
  expensive than carrying an unused column.
- Parameterized queries only. `sqlc` makes this the default rather than a discipline.

## Consequences

- Transactional guarantees where they matter most: job leasing, backup/verification state
  transitions.
- `sqlc` gives compile-time-checked SQL and typed Go structs with no ORM indirection.
- Postgres is already required in the dev stack, and it is the engine of the reference plugin, so
  the operational surface stays small.
- Cost: an operator must run a Postgres for Fleetward itself. Acceptable — the target user is a DBA.

## Alternatives considered

- **SQLite.** Attractive for single-node simplicity, but poor fit for concurrent job leasing and a
  dead end for the eventual HA control plane.
- **An ORM (GORM/ent).** Hides the SQL we most need to reason about, particularly around leasing
  and tenant scoping.
